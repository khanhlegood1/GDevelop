## 2. Kết quả probe local mới (24/10/2026, UTC)

### 2.1 Phương pháp (quyết định D1–D3)

- **Mỗi phase một dev server tươi** (memory store, Dev Auth, invite seed) —
  kill cả process group bằng `setsid`, có xác minh port thực sự tự do; tránh
  nhiễm strike/state giữa các phase.
- **Hai chế độ policy có chủ đích:** probe hành vi (security, guard) chạy với
  **R1.10 policy mặc định**; probe **latency** chạy với guard nới qua
  `GON_ABUSE_*` env (ghi rõ trong script) — vì flood window mặc định
  **120 strikes/10 giây/IP** sẽ box chính benchmark giữa chừng (đã quan sát
  thực tế trong lần chạy thử: 429 xuất hiện đúng sau ~120 request). Đo latency
  mà bị 429 xen lẫn sẽ tạo số liệu không so sánh được với baseline P05 gốc.
- **Guard-engagement là phase dương tính:** kỳ vọng 429 — không coi 429 là lỗi.

### 2.2 Kết quả

**Phase 1 — DAST-equivalent security probe (default policy): 7/7 PASS**
(401 AUTH_REQUIRED bootstrap ẩn danh; 403 CSRF khi thiếu token; 403 khi spoof
`X-Forwarded-Host`; 400 khi thiếu Idempotency-Key; 400 JSON lỗi có kiểm soát;
giới hạn body 2,5 MB; headers an toàn). Chi tiết: `results/*-security-probe.json`.

**Phase 2 — Benchmark baseline (relaxed guards; so được với P05 review gốc):**

**Phase 3 — Heavy pass (relaxed; 20 workers):** read 80×80×80 endpoint = toàn
200; search 20× = toàn 202 (p95 26,8 ms); concurrent 150 bootstrap p50 299 /
p95 445 ms, 61,8 rps, toàn 200. Không 5xx, không lỗi giao thức.

**Phase 4 — Guard-engagement (default policy) — controls ENGAGED:**
400 GET ẩn danh liên tiếp → **đúng 120 request đầu trả 401, 280 request sau
trả 429 `RATE_LIMITED` kèm header `Retry-After`** — khớp chính xác ngưỡng
`flood.strikeLimit = 120` của `DEFAULT_ABUSE_POLICY`. Đây là bằng chứng
local trực tiếp (lần đầu đo end-to-end qua HTTP) rằng kiểm soát R1.10 ở tầng
origin bật đúng thiết kế. Chi tiết: `results/*-guard-engagement.json`.

### 2.3 Nhận định

- Số liệu latency local **không suy ra SLO staging** (memory store, dev
  server, 1 user) — giữ nguyên nhãn như NFR-SPECIFICATION.
- Phát hiện có giá trị: tương tác giữa probe tổng hợp và flood guard mặc định —
  benchmark > 120 request/10s từ 1 IP sẽ bị box 30 s. Với người dùng thật
  Private Alpha (vài chục request/phút) ngưỡng này rộng; **tuy nhiên cần đo
  lại trên staging** và PO có thể chỉnh `GON_ABUSE_FLOOD_STRIKE_LIMIT` nếu
  muốn dày hơn (đã có env, không cần code).

## 4. P05 re-review — đề xuất cho PO

**Kết luận đề xuất: P05 giữ nguyên IN REVIEW — NOT YET PASS.**

thành với bằng chứng local/hermetic đầy đủ; **không còn remediation local nào

2. Duyệt `staging-checklist.md` làm **cơ sở nghiệm thu P06** (mục §1–§10).
3. Duyệt phương pháp probe R1.15 (default-policy cho hành vi; relaxed-policy
   cho latency; guard-engagement dương tính) để chạy lại tương tự trên staging.

5. Khi GitHub Actions chạy lại: bật required checks (GON CI các job) — việc
