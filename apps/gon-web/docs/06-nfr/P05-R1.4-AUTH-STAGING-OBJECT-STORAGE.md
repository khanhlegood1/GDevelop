## 1. Đã triển khai

### 1.1 Auth.js configuration và identity provisioning

`src/server/auth.ts` nay chỉ là composition root mỏng. Toàn bộ options có thể kiểm thử được chuyển vào `src/server/auth-config.ts`:

- `resolveAuthEnv` chọn một cặp Google credentials nhất quán (`AUTH_GOOGLE_*` hoặc `GOOGLE_CLIENT_*`), chuẩn hóa `AUTH_SECRET`/`NEXTAUTH_SECRET`, và giữ `AUTH_TRUST_HOST` mặc định tắt ở production.
- Khi có PostgreSQL adapter, session strategy là `database`, `maxAge` 30 ngày và `updateAge` 24 giờ. JWT vẫn là fallback local khi không có adapter.
- `signIn` chỉ chấp nhận Google account có `providerAccountId` và profile email đã `email_verified=true`.
- Hai lỗi contract được sửa:
  1. **First-login identity bug:** Auth.js gọi `signIn` trước khi adapter tạo Auth user ở lần OAuth đầu tiên, nên `user.id` tại thời điểm đó có thể là Google subject chứ chưa phải ID của row `users`. Code cũ provision GON identity ngay tại callback này và có nguy cơ lưu sai `auth_user_id`, làm session đầu tiên không map được sang GON user. Nay `signIn` không ghi domain identity; `events.signIn`—điểm Auth.js gọi sau khi user/account/session đã được persist—mới gọi `ensureGoogleUser` bằng đúng Auth user ID + Google provider subject.
  2. **Session-token exposure:** database-session callback không còn trả nguyên object session Auth.js truyền vào. Nó chỉ trả allow-list `expires` và `user{name,email,image,gonUserId}`, không để `sessionToken`/`userId` nội bộ xuất hiện ở JSON `/api/auth/session`.
- JWT fallback cũng được nối nhất quán: `jwt` callback provision/map `gonUserId` từ persisted/provider identity ở thời điểm sign-in và giữ lại claim ở các request sau.
- Actor resolution phía server vẫn kiểm tra lại GON user theo `gonUserId`; user đã `deleted` không tạo actor.

> **Lưu ý vận hành:** nếu một môi trường thử nghiệm cũ đã tạo GON identity bằng đường `signIn` cũ ở lần đăng nhập đầu, session hiện hữu có thể cần đăng xuất/đăng nhập lại một lần để `events.signIn` cập nhật `auth_user_id` về đúng Auth database ID. Chưa có dữ liệu production nên không cần backfill ở baseline hiện tại.

### 1.2 Bằng chứng adapter/session trên PostgreSQL engine

Thêm `tests/integration/postgres-auth-object-storage.test.ts`. Test áp dụng đủ 7 migrations trên PGlite/PostgreSQL WASM và dùng chính `@auth/pg-adapter` bản production đang khóa trong lockfile:

- `createUser`, `linkAccount`, `getUserByAccount` cho Google subject;
- `events.signIn` tạo đúng `identity_links(provider='google', provider_subject=...)` và `gon_users.auth_user_id`;
- `createSession` + Auth core session handler trả đúng `gonUserId` và không lộ session token;
- `deleteSession` làm session bị thu hồi ngay ở request kế tiếp;
- session hết hạn bị từ chối và row bị Auth core dọn;
- `updateSession` đổi expiry trong DB.

Production `auth.ts` dùng NextAuth wrapper với cùng options. Test hermetic gọi Auth core handler mà NextAuth ủy quyền tới để không phụ thuộc Next dev-server module loader. Đây là bằng chứng chặt cho adapter SQL, expiry/revoke và session callback, nhưng **không thay thế** việc chạy OAuth redirect/consent thật qua Google và Next route trên staging.

### 1.3 Readiness fail-closed cho Auth

`ReadinessReport` có thêm check `auth` và `objectStorage` ở phía server (route công khai vẫn chỉ trả `ready|not_ready`):

- production chỉ ready khi object storage là GCS đã cấu hình; memory/filesystem nhận `OBJECT_STORAGE_NOT_DURABLE`.

### 1.4 Private object-storage port

Thêm:

- `src/server/object-storage-config.ts` — parse/validate env không lộ secret;
- `src/server/object-storage.ts` — interface `ObjectStorage` và bốn adapter:
  - `RepositoryObjectStorage`: tương thích local/test qua repository map hiện có;
  - `InMemoryObjectStorage`: process-local tường minh cho local/test;
  - `FilesystemObjectStorage`: ghi atomically bằng temp file + rename, metadata sidecar, khóa path trong root cấu hình;
  - `GoogleCloudStorageObjectStorage`: adapter GCS private không cần SDK mới.

Mọi adapter chỉ nhận key bắt đầu `private/`, từ chối traversal/backslash/control characters và áp dụng giới hạn khi server download bytes.

#### GCS adapter

- Tạo **V4 signed PUT** tối đa 15 phút; chữ ký bind `Content-Type`, host và metadata `x-goog-meta-gon-sha256` bằng RSA-SHA256.
- Browser không nhận local upload token trong GCS mode và không gửi cookie GON cross-origin tới signed URL.
- Metadata/download/delete phía server dùng service-account JWT → OAuth access token có cache theo expiry; download đọc theo stream và hủy khi vượt `maxBytes`.
- `putObject` phía server dùng resumable-upload protocol để ghi custom SHA-256 metadata và tránh giới hạn 5 MB của simple upload; bearer token không được gắn vào resumable session URI.
- Lỗi GCS chỉ mang machine code/status an toàn, không log private key, signed URL hay provider response body.

#### Runtime configuration

| Biến | Ý nghĩa |
|---|---|
| `GON_OBJECT_STORAGE=memory\|filesystem\|gcs` | Chọn adapter; mặc định `memory` chỉ cho local/test |
| `GON_LOCAL_OBJECT_DIR` | Root bắt buộc khi dùng filesystem; phù hợp một host/PVC, không phải multi-instance Cloud storage |
| `GON_GCS_BUCKET` | Tên private bucket |
| `GON_GCS_SERVICE_ACCOUNT_EMAIL` | Service account ký/gọi GCS JSON API |
| `GON_GCS_SERVICE_ACCOUNT_PRIVATE_KEY` | PEM private key; hỗ trợ dạng newline thật hoặc literal `\n` từ Secret Manager |

Composition production từ chối memory/filesystem, trừ override cô lập đã có `GON_ALLOW_MEMORY_STORE_IN_PRODUCTION=1`. Override đó không biến local bytes thành production persistence và readiness production vẫn yêu cầu GCS.

### 1.5 Domain upload flow qua storage port

`GonService` nhận `objectStorage` như một dependency tường minh; `GonServiceCore` không còn đọc/ghi trực tiếp `repositories.objects` ngoài adapter tương thích mặc định:

- **Initiate:** tạo signed-upload plan từ adapter trước khi persist artifact/session. Local adapter trả `/api/local-uploads/{id}` + one-time token; GCS trả signed URL + signed headers.
- **Local PUT:** vẫn authorize trước khi HTTP route đọc body. Endpoint này bị vô hiệu trong GCS mode để tránh fallback về process-local bytes.
- **Complete:** `headObject` trước, chặn object lớn hơn giới hạn document, kiểm tra thời điểm ghi so với session expiry cho direct upload, download bounded rồi **tự tính lại byte size + SHA-256 từ bytes thật**. Local accepted hash bị thay đổi phía storage, client hash/size khác object, hoặc object khác declaration đều bị chặn trước extraction.
- **Retry/delete:** đều đi qua port. Delete xóa bytes trước commit để fail về phía privacy; thao tác xóa của adapter là idempotent để retry được sau rollback.
- **UI:** `resolveUploadRequest` giữ nguyên HTTPS signed URL cross-origin và dùng `credentials: omit`; URL same-origin vẫn dùng cookie/CSRF boundary của local simulator.

PostgreSQL integration test tạo project/upload session bằng một service instance, ghi bytes vào shared fake direct storage, rồi complete bằng **service/store instance mới**. Artifact chỉ hoàn tất khi bytes lấy từ storage port; DB ghi đúng actual hash/completion và chunks. Đây là bằng chứng trực tiếp cho việc tách raw bytes khỏi PostgreSQL Unit-of-Work map.

## 3. Những gì vẫn phải chứng minh trên staging thật

Các mục dưới đây vẫn là **NOT RUN**, không được suy diễn từ PGlite/fake fetch:

1. **Google OAuth thật:** tạo OAuth client riêng cho staging, redirect URI `/api/auth/callback/google`, test first sign-in/repeat sign-in/sign-out/revoke từ Google account settings, session cookie qua HTTPS/proxy và `AUTH_TRUST_HOST` chỉ khi edge đã chứng minh ghi đè forwarded headers.
2. **Account lifecycle E2E:** invite hết hạn/đã dùng, onboarding chưa xong, suspended, deletion-pending/deleted, đổi email/tên Google và nhiều browser session đồng thời.
3. **GCS thật:** bucket private có uniform bucket-level access + public-access prevention; service account chỉ có quyền object cần thiết trên đúng bucket; secret qua Secret Manager; CORS chỉ cho origin staging, method `PUT`, headers `Content-Type` và `x-goog-meta-gon-sha256`; kiểm tra signed PUT/complete/delete bằng trình duyệt thật. Adapter hiện tại ký bằng PEM private key; nếu chính sách tổ chức cấm tải service-account key, phải bổ sung biến thể Workload Identity/IAM `signBlob` trước staging thay vì nới lỏng chính sách chỉ để chạy adapter này.
4. **Object lifecycle/cost:** signed PUT hiện không bind cứng content length trong chữ ký; GON chỉ enforce ở complete. Cần staging policy/report cho orphan và object quá hạn/chưa complete, incomplete resumable cleanup, versioning/retention và đối soát DB key trước khi xóa theo tuổi. Không đặt lifecycle xóa toàn bộ `private/` theo tuổi vì đó cũng là prefix của artifact đang hoạt động.
5. **Managed PostgreSQL/network:** lặp lại adapter/domain tests trên Cloud SQL/managed PostgreSQL với TLS/IAM, pool/timeout, clock, backup/restore và tải đồng thời.
6. **Upload safety sâu hơn:** storage boundary không thay malware scan, parser sandbox, image/PDF decompression limits hay kiểm chứng nội dung độc hại.
7. **Tính nguyên tử xuyên hệ thống:** GCS/filesystem không tham gia DB transaction. Signed object có thể thành orphan nếu DB commit fail; delete có thể xóa bytes trước khi metadata commit fail. Cần deletion/orphan reconciliation job qua durable queue/outbox ở lát cắt vận hành sau.
8. **Transaction boundary:** head/download/delete external vẫn diễn ra bên trong Unit-of-Work hiện tại. Targeted repositories và transaction ngắn quanh external calls vẫn là nợ hiệu năng/độ tin cậy.
